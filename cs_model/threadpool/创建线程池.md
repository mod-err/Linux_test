## 1 资源释放

### 1. 逐行解释
```c
if (pool && pool->threadIDs) free(pool->threadIDs);
if (pool && pool->taskQ) free(pool->taskQ);
if (pool) free(pool);
return NULL;
```
- `pool && pool->threadIDs`：先判断 `pool` 本身是否非空，再判断 `pool->threadIDs` 是否非空。只有两者都非空，才释放 `threadIDs` 指向的内存。
- 同理，释放 `taskQ`。
- 最后，如果 `pool` 非空，释放 `pool` 本身。
- 返回 `NULL`，告诉调用者创建失败。

### 2. 为什么能安全地这样判断？
关键在于 `threadPoolCreate` 中 `do { ... } while(0)` 的流程控制：
- 如果 `malloc(pool)` 失败，`pool` 为 `NULL`，直接 `break`。后面 `if (pool && ...)` 由于短路求值，不会访问 `pool->threadIDs`，安全。
- 如果 `malloc(pool->threadIDs)` 失败，`pool->threadIDs` 被赋值为 `NULL`（`malloc` 失败返回 `NULL`），`break` 后 `if (pool && pool->threadIDs)` 为假，不会错误释放。
- 如果后续的 `pthread_mutex_init` 等失败，此时 `threadIDs` 和 `taskQ` 都已经成功分配，所以会被正确释放。

### 3. 释放顺序很重要
必须**先释放结构体内部的动态成员**（`threadIDs`、`taskQ`），**最后释放结构体本身**（`pool`）。
如果先 `free(pool)`，那么 `pool->threadIDs` 和 `pool->taskQ` 就无法访问了（悬垂指针），会导致内存泄漏。你给出的代码顺序是正确的。

### 4. 这种写法的意义
在 C 语言中，一个函数可能因为多种原因失败（内存不足、锁初始化失败等），如果没有统一的清理逻辑，就需要在每个失败点重复写释放代码，容易遗漏。使用 `do { ... } while(0)` 配合 `break`，可以把所有失败都汇聚到一处清理，既简洁又安全。这是 C 语言中处理多重资源分配的经典模式。

### 5. 小提醒
如果 `pool` 非空但 `threadIDs` 从未被赋值过（比如 `malloc(pool)` 成功后，第一件事就是赋值 `threadIDs`，所以这种情况不存在）。因此这里的判断是完备的。

## 2 do while(0)妙用

### 2. 巧妙的错误处理模式（`do-while(0)`）
```c
ThreadPool* pool = (ThreadPool*)malloc(sizeof(ThreadPool));
do 
{
    if (pool == NULL) { ...; break; }
    // ... 其他初始化 ...
    return pool;
} while (0);

// 统一错误处理（释放已分配的内存）
// ...
return NULL;
```
**为什么这么写？**
在 C 语言中，如果中间某一步失败（比如 malloc 失败），你需要释放前面已经申请好的资源，代码会变得非常冗长（大量嵌套 `if` 或 `goto`）。
这里的 `do { ... } while(0)` 是一个**只执行一次**的代码块。一旦某一步失败，直接 `break`，就会跳到 `while(0)` 后面的**统一清理代码**，释放资源并返回 `NULL`。这种写法既优雅又安全。

### 4. 错误清理（优雅的兜底）
```c
// 释放资源
if (pool && pool->threadIDs) free(pool->threadIDs);
if (pool && pool->taskQ) free(pool->taskQ);
if (pool) free(pool);
return NULL;
```
如果 `do-while` 里任何一步失败执行了 `break`，代码会来到这里：
1. 先检查 `pool` 是否存在。
2. 再检查 `pool->threadIDs` 和 `pool->taskQ` 是否已经分配了内存。
3. 层层释放，避免内存泄漏。
4. 返回 `NULL` 告知调用者创建失败。

### 💡 架构小结
这个创建函数体现了三个高并发服务器设计的核心思想：
1. **内存预分配**：`threadIDs` 一次性按 `max` 分配，避免运行中扩容。
2. **细粒度锁**：`mutexPool` 和 `mutexBusy` 分开，减少锁竞争。
3. **生产者-消费者模型**：通过 `notEmpty` 和 `notFull` 这对条件变量，完美协调“添加任务”和“处理任务”两方的节奏。
