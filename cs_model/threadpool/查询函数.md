这两个函数是线程池的**状态查询接口**，用于安全地获取线程池当前的运行状态。它们结构几乎一样，只是查询的变量和使用的锁不同。

---

### 一、`threadPoolBusyNum`：查询忙线程数量

```c
int threadPoolBusyNum(ThreadPool* pool)
{
    pthread_mutex_lock(&pool->mutexBusy);   // 1. 加锁
    int busyNum = pool->busyNum;            // 2. 读取忙线程数
    pthread_mutex_unlock(&pool->mutexBusy); // 3. 解锁
    return busyNum;                         // 4. 返回副本
}
```

**作用**：返回当前正在执行任务的线程数量。

**流程**：
1. 加 `mutexBusy` 锁（专门保护 `busyNum` 变量的锁）。
2. 把 `pool->busyNum` 读到一个局部变量里。
3. 解锁。
4. 返回局部变量的值。

**为什么要加锁？**
`busyNum` 会被多个工作线程同时修改：线程开始执行任务时 `busyNum++`，任务完成后 `busyNum--`。如果不加锁，查询到的值可能是“半成品”或者与实际情况不一致。加锁保证读到的是一个完整的、一致的值。

**为什么用局部变量再返回？**
不能在 `pthread_mutex_unlock` 之后再访问 `pool->busyNum`，因为解锁后其他线程可能立刻修改它。所以必须在锁内把值拷贝出来，解锁后返回拷贝的值。

---

### 二、`threadPoolAliveNum`：查询存活线程数量

```c
int threadPoolAliveNum(ThreadPool* pool)
{
    pthread_mutex_lock(&pool->mutexPool);   // 1. 加锁
    int aliveNum = pool->liveNum;           // 2. 读取存活线程数
    pthread_mutex_unlock(&pool->mutexPool); // 3. 解锁
    return aliveNum;                        // 4. 返回副本
}
```

**作用**：返回当前线程池中存活的线程数量（包括空闲的和忙的）。

**与上一个函数的区别**：
- 保护的是 `liveNum`，用的是 `mutexPool` 这把大锁。
- `liveNum` 会被管理者线程、工作线程修改（新增或销毁线程时），所以必须用保护整个线程池的 `mutexPool`。
- 而 `busyNum` 修改频繁，单独用 `mutexBusy` 锁，避免所有操作都去抢 `mutexPool`，提高并发效率。

---

### 三、为什么要单独提供这两个函数？

直接访问 `pool->busyNum` 或 `pool->liveNum` 是不安全的，因为它们随时可能被其他线程修改。这两个函数把“加锁 → 读值 → 解锁”封装起来，对外提供一个**线程安全**的查询接口。

典型使用场景：
- **日志/监控**：管理者线程定期打印当前忙线程数和存活线程数。
- **动态扩容/缩容**：管理者线程根据忙线程数决定是否增删工作线程。
- **调试**：测试时随时查看线程池状态。

---

### 四、对比总结

| 函数 | 查询对象 | 使用的锁 | 变量含义 |
|------|----------|----------|----------|
| `threadPoolBusyNum` | `busyNum` | `mutexBusy` | 正在执行任务的线程数 |
| `threadPoolAliveNum` | `liveNum` | `mutexPool` | 当前存活的线程总数 |

---

### 五、一个常见细节

这两个函数都没有做 `pool == NULL` 检查。如果调用者传入空指针，会直接崩溃。如果希望更健壮，可以在开头加：

```c
if (pool == NULL) return -1;
```

不过在实际代码中，调用者通常已经确认 `pool` 有效，所以这里省略也可以。

**一句话总结**：这两个函数就是线程池的“仪表盘”，让你安全地查看当前有多少线程在干活、总共有多少线程活着。😊
